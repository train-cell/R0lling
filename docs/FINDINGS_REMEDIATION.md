## Shamir 2-of-3 format contract

- The API splits the exact UTF-8 bytes of one non-empty string, up to 1 MiB, into three shares; any two are sufficient.
- Shares use a canonical unpadded Base64URL envelope (`r0ss1.`), fixed version/algorithm/threshold fields, a random 128-bit set identifier, coordinate, bounded secret length, payload, and a 32-byte HMAC-SHA256 tag.
- Arithmetic is over GF(2^8) with the AES irreducible polynomial `0x11B`. Each secret byte and a separate random 32-byte validation key are independently shared with a uniform random slope. The validation key authenticates the set metadata, coordinate, and payload; no unkeyed hash of a low-entropy secret is placed in the shares.
- Apple builds obtain coefficients, validation key, and set identifier from checked `SecRandomCopyBytes` calls. Random-source failure throws; it does not fall back to a non-cryptographic generator.
- Reconstruction rejects malformed/noncanonical input, unsupported metadata, wrong lengths, oversized shares, duplicate coordinates, mixed set identifiers, inconsistent triples, bad tags, and invalid UTF-8. HMAC authenticates share integrity; it does not encrypt share strings, provide recovery UI, or guarantee Swift memory zeroization.
- Mathematical basis: [Shamir’s original threshold-sharing paper (MIT, 1979)](https://dspace.mit.edu/entities/publication/91c51bfc-5678-409c-80c5-44ce8fcdbadf). The GF(2^8) representation follows the AES field in [NIST FIPS 197](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.197.pdf). Apple documents [cryptographically secure `SecRandomCopyBytes`](https://developer.apple.com/documentation/security/secrandomcopybytes%28_%3A_%3A_%3A%29?language=objc) and [HMAC authentication/validation in CryptoKit](https://developer.apple.com/documentation/cryptokit/hmac).
